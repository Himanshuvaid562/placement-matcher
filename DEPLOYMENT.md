# Deployment Guide

Target setup: **MongoDB Atlas** (database) + **Render** (Express API) + **Vercel** (Next.js frontend).
Deploy in this order, because each step needs a URL from the previous one.

> Not yet verified end-to-end: the Docker images, `render.yaml` and the CI workflow were written and
> checked for syntax, but I could not run Docker, Render or GitHub Actions from the authoring environment.
> Expect to fix small things on the first deploy, and treat the first CI run as the real test of the
> database-backed integration tests.

## 1. MongoDB Atlas
1. Create a free **M0** cluster.
2. **Database Access** -> add a database user with a strong generated password (readWrite on one database is enough).
3. **Network Access** -> Render's free tier has no fixed outbound IPs, so Atlas will need to allow `0.0.0.0/0`.
   That is acceptable only because the database user has a strong password and TLS is enforced. If you move to a
   paid Render plan with static outbound IPs, restrict the allowlist to those.
4. **Connect -> Drivers** -> copy the connection string and add the database name:
   `mongodb+srv://<user>:<password>@<cluster>.mongodb.net/p06_placement?retryWrites=true&w=majority`

## 2. Backend on Render
1. Push the repo to GitHub. In Render choose **New -> Blueprint** and select the repo (it reads `render.yaml`),
   or create a Web Service manually with root directory `backend`, build `npm ci --omit=dev`, start `node src/server.js`.
2. Set the environment variables:

| Variable | Value |
|---|---|
| `MONGO_URI` | the Atlas string from step 1 |
| `JWT_SECRET` | auto-generated by the blueprint (must be 32+ chars; the server refuses to start otherwise) |
| `OFFICER_INVITE_CODE` | a long secret you choose; needed to create officer accounts |
| `CORS_ORIGIN` | your Vercel URL (set after step 3), comma-separate multiple origins |
| `PUBLIC_APP_URL` | your Vercel URL: recruiter verification links are built from it |
| `CERTIFICATE_LEVEL_CAP` | optional, default `3` |
| `NODE_ENV` | `production` |

3. Confirm `https://<your-api>.onrender.com/health` returns `{"status":"ok"}`.

Free-tier Render services sleep when idle, so the first request after a pause can take ~30-60 s.

## 3. Frontend on Vercel
1. **Add New Project**, import the repo, set **Root Directory** to `frontend`.
2. Environment variable: `NEXT_PUBLIC_API_URL` = `https://<your-api>.onrender.com/api`
   (this is baked in at build time, so redeploy after changing it).
3. Deploy, then go back to Render and set `CORS_ORIGIN` to the Vercel URL.

## 4. Create the first Placement Officer
Officer accounts cannot be self-registered without the invite code.
1. Open `/register` on your site, choose **Faculty / Placement Officer**, enter your employee ID (5+ digits), a password, and your `OFFICER_INVITE_CODE`.
2. Log in, add skills (`/admin/skills`) and companies, then create and publish opportunities.
3. Open **Verification -> Import official records** and upload your university's CSV export
   (format: `sample-data/official-records.csv`). Students are only treated as eligible after an officer approves them there.
4. Share the invite code only with placement staff, and rotate it (change the env var) once your team is set up.

**Never run `npm run seed` against production.** It deletes all data and creates demo accounts with known passwords;
it refuses to run when `NODE_ENV=production` unless `SEED_FORCE=1` is set.

## Alternative: single VPS with Docker
```
export JWT_SECRET=$(node -e "console.log(require('crypto').randomBytes(48).toString('hex'))")
export OFFICER_INVITE_CODE=choose-a-long-secret
export CORS_ORIGIN=https://placement.example.edu
export NEXT_PUBLIC_API_URL=https://api.placement.example.edu/api
docker compose up --build -d
```
Put a TLS-terminating reverse proxy (Caddy/nginx) in front of ports 3000 and 5000. MongoDB is deliberately
not published to the host in this compose file.

## Certificate storage
Uploaded certificate PDFs are stored **inside MongoDB** (3 MB max each, 25 per student), so they survive redeploys on hosts with
ephemeral disks such as Render. Atlas M0 has 512 MB, so watch usage: roughly 1,000 students with a few 500 KB certificates each is fine,
but a heavy-use campus should move files to object storage (S3/Cloudinary). Certificates are student documents: include this
collection in your backups and your retention/deletion rules. Deleting a certificate removes its PDF.

## Recruiter verification links
`/verify/<token>` is the only page that works without a login. It is rate-limited per IP and never indexed by search engines (`X-Robots-Tag`),
but anyone holding a link can open it until it expires or the student revokes it. Set `PUBLIC_APP_URL` correctly or links will point at localhost.

## Pre-launch checklist
- [ ] `JWT_SECRET` and `OFFICER_INVITE_CODE` are unique, random, and not committed anywhere
- [ ] HTTPS everywhere; `CORS_ORIGIN` lists only your real frontend origin(s)
- [ ] CI is green with the database-backed tests actually running (`REQUIRE_DB_TESTS=1`)
- [ ] Atlas backups enabled (student academic records are personal data)
- [ ] `PUBLIC_APP_URL` is your real frontend address (recruiter links), and you have opened one in a private window
- [ ] Decide who may open students' certificates (all officers can) and how long they are kept
- [ ] Decide who may use the CSV export (it contains student emails) and document retention rules
- [ ] Demo accounts from the seed script (IDs 10001, 12000001, 12000002) do not exist in production
- [ ] Existing database from an older (email-login) version? Users must re-register; the server drops the stale `email` index at startup

## Known limitations to revisit
- **Known dependency advisory (`zod` 3.x, high):** `npm audit` reports that validating *very large* arrays can use a lot of memory. The fix is zod 4,
  which is a breaking change (schemas and error shapes differ), so it has not been applied. It is mitigated here because every JSON body is capped
  (100 KB; 2 MB only on the officer's bulk record import, itself limited to 5,000 rows) and every array in a schema has a small `.max()`.
  Plan a zod 4 migration, then run `npm audit` again. The `multer` and `qs` advisories were fixed by updating them.
- The recruiter verification page (`/verify/<token>`) is served with `noindex` and `no-referrer`, because its URL contains the secret token. The token also appears in the
  frontend host's access logs, so treat those logs as sensitive and keep link expiry short.
- Faculty accounts have no self-service password recovery yet (students are recovered by an officer). Until then, keep a second officer account.
- The JWT is kept in `localStorage`, so an XSS bug would expose sessions. Moving to an httpOnly cookie
  (with CSRF protection) is the stronger design.
- There is no UMS single sign-on: users have separate passwords for this app (integration needs LPU IT to provide SSO).
- Sessions are checked against the database on every request, so password changes, resets and disabled accounts take effect immediately (one extra lookup per request).
- A student can retake an assessment and the latest score overwrites the verified level for the linked skill.
